# 03 — Functional specification

## 0. Core concepts

| Concept | Meaning |
| --- | --- |
| **Engine family** | A kind of execution system with its own submission, driver program and telemetry reader. v1.0 ships one family: `spark`. Other families (for example Trino, Flink batch, DuckDB) plug in later through the same interfaces (section 4) |
| **Engine** | One member of a family: container image + configuration (`spark-vanilla`, `spark-gluten`, `spark-comet`, a vendor accelerator) |
| **Workload** | A set of units of work plus the data they need. Kind `sql` (queries) or `job` (general Spark programs) |
| **Unit of work** | The smallest timed and checked thing: one SQL query, or one step of a job (for example TeraSort's sort phase). Identified by `unit_id` |
| **Measure** | A number computed per unit and repetition: wall time, CPU time, cost, or any custom unit of measure (section 6) |
| **Cell** | One combination of workload × engine × cluster × config × format × mode |

## 1. Workloads

### 1.1 SQL workloads

| Workload | Notes |
| --- | --- |
| TPC-H-derived (22 queries) | Smoke and development set |
| TPC-DS-derived (99 queries) | Main SQL set |
| Bring-your-own SQL | SQL files plus a dataset manifest |

TPC results are always labeled "derived from TPC-H / TPC-DS". The project never vendors TPC kits; data is generated at runtime.

### 1.2 General job workloads

Classic Apache Spark job benchmarks, reimplemented in this repo under Apache-2.0 (no third-party benchmark code is vendored):

| Job | Units | Correctness check | API |
| --- | --- | --- | --- |
| TeraGen → TeraSort → TeraValidate | `teragen`, `terasort` | Output globally sorted; record count and order-independent checksum equal to input | Scala (RDD) |
| Sort | `sort` | Sorted; checksum equals input | Scala (RDD) |
| WordCount | `wordcount` | Checksum of (word, count) pairs | Scala (RDD) and PySpark (DataFrame) |
| PageRank (power-law graph) | `pagerank` | Ranks within a tolerance of the reference engine (iterative floats differ by engine) | Scala (RDD) and DataFrame |
| KMeans (MLlib) | `kmeans-train` | Cost within a tolerance; same iteration count | PySpark (MLlib) |
| ETL pipeline | `read`, `clean`, `join`, `aggregate`, `write` | Checksum of the written output | PySpark (DataFrame) |
| Bring-your-own job | Declared by the job, or the whole application as one unit | Validator supplied with the job, or `not_checked` | Any |

RDD jobs are written in Scala (a small `velocia-jobs` jar built per Spark/Scala version) so that they measure the engine, not Python worker overhead. DataFrame jobs are PySpark because their plans run on the JVM anyway. Most accelerators speed up SQL/DataFrame operators, not RDD code. RDD jobs therefore show how much of a real job falls back to vanilla execution, and reports state this explicitly.

**Timed sinks.** SQL units write to the `noop` sink. A job declares its sink: `noop`, or `write` to a scratch location that is deleted after the run (TeraSort's cost includes writing its output). The sink is recorded in the manifest.

**Tagging.** Jobs mark units with a small helper: Python `with velocia.unit("terasort"):` and Scala `Velocia.unit("terasort") { ... }`. The helper sets the job description to the unit tag and records wall time. An unmodified third-party job is one opaque unit timed from the application start/end in its event log.

### 1.3 Edge-case and stress workloads (`synth` suite)

Generated by Velocia from a seeded generator, so every dataset is reproducible from its manifest. Each workload sweeps one parameter and reports a curve with CIs (this replaces the earlier "operator probes" list):

| Workload | Swept parameter |
| --- | --- |
| Skewed join | Zipf exponent of the join key (0 = uniform … 1.5), with and without AQE skew-join handling |
| Hot key | Fraction of rows on a single key (0.1% → 50%) |
| Skewed aggregate | Zipf exponent of the group key; group cardinality |
| Exploding join | Many-to-many fan-out factor |
| Spill | Executor memory as a fraction of the working set |
| Shuffle partitions | Partition count from very few (huge partitions) to very many (tiny tasks) |
| Small files | File count at constant total size (10 → 100,000 files) |
| Wide rows | Column count (10 → 2,000), projecting 5 |
| Nested types | Struct/array/map depth; `explode` fan-out |
| Null-heavy | Null fraction per column |
| Decimal precision | `decimal(38, s)` arithmetic and aggregation |
| Strings | Length, regexp and `LIKE` patterns, multi-byte UTF-8 |
| Scan + filter selectivity | 0.1% → 90% |
| Join strategy | Broadcast vs sort-merge across build-side size |
| Window functions | Partition size and frame type |
| UDF fallback | A Python UDF or pandas UDF in the middle of a plan |

## 2. Data

- `velocia datagen --suite tpch|tpcds --sf N --format parquet-snappy|parquet-zstd [--iceberg]`.
- `velocia datagen --suite tera --rows N`, `--suite text --bytes N`, `--suite graph --vertices N --edges N`, `--suite kmeans --points N --dims D`.
- `velocia datagen --suite synth --spec synth.yaml`: rows, key distribution (`uniform`, `zipf(s)`, `hotkey(fraction)`), cardinality, null fraction, column count and types, nesting depth, string-length distribution, file count, seed.
- SF1–SF10 through DuckDB extensions; larger scale factors through the official kit installed by the user (documented, not bundled). Tera, text, graph, KMeans and synth data are generated by Spark jobs in the engine image (seeded), so they scale with the cluster.
- Dataset manifest: suite, generator parameters and seed, scale, format, compression, row-group size, file count, total bytes, checksum.

## 3. Experiments

Declared in YAML (schema in 04), expanded into cells = workload × engine × cluster × config × format × mode.

```yaml
name: tpch-engines-sf10
workload: {kind: sql, suite: tpch, units: all, scale_factor: 10, format: parquet-zstd}
engines: [spark-vanilla, spark-gluten, spark-comet]
reference_engine: spark-vanilla
cluster: {runner: k8s, executors: 4, executor_cores: 4, executor_memory: 8g}
spark_conf:
  spark.sql.adaptive.enabled: [true, false]
measures: [wall_time, task_cpu_time, cost_usd]
repetitions: 5
modes: [cold, warm]
```

Comparing engines on different hardware (for example vanilla Spark on CPU nodes vs Spark on hardware-accelerator nodes such as Speedata's APU) uses named clusters, each engine pinned to one, and the explicit cross-hardware override:

```yaml
name: terasort-cpu-vs-apu
workload: {kind: job, suite: tera, units: [terasort], rows: 1e10}
clusters:
  cpu:   {runner: k8s, node_selector: {pool: cpu},   executors: 8, executor_cores: 8, executor_memory: 32g, hardware_profile: cpu-m6i}
  apu:   {runner: external, master: "spark://apu-host:7077", deploy_mode: client,
          executors: 2, executor_cores: 8, executor_memory: 32g, hardware_profile: apu-node,
          data_uri: "s3a://bench/velocia/", eventlog_uri: "s3a://bench/velocia/eventlog/"}
engines:
  - {name: spark-vanilla, cluster: cpu}
  - {name: spark-apu, cluster: apu}
reference_engine: spark-vanilla
comparison: {allow_cross_hardware: true}
measures: [wall_time, node_hours, accelerator_hours, cost_usd]
repetitions: 5
modes: [cold]
```

`velocia run --dry-run` prints the expanded cells, estimated run count and estimated duration before anything starts.

## 4. Runners, engine families and engines

- **Runners** (plugin): `local` (Docker, Spark standalone or `local[*]`), `k8s` (Spark Operator `SparkApplication`, with node selectors, tolerations and extended resources such as accelerator devices), `external` (v0.2). v0.3: one cloud provider.
- **`external` runner** (v0.2): submits to a Spark cluster that Velocia does not create or manage, such as a vendor's accelerator servers that expose the regular Spark API. It runs `spark-submit` against a given master URL (standalone, YARN or Kubernetes) with Velocia's driver program, `velocia-jobs` jar and Spark conf. The vendor's own Spark build stays as is; Velocia adds nothing to it. Requirements and limits:
  - Data: datasets are copied to, or generated on, the cluster's storage (`data_uri`); the dataset checksum is verified there before the first run.
  - Event logs: the run sets `spark.eventLog.dir` to `eventlog_uri`, and the collector downloads the finished logs from there. If the logs can't be fetched, the run still reports driver timings, but event-log measures are `null` with a reason and the run is flagged.
  - Hardware: no probe runs on nodes Velocia doesn't control, so the hardware profile declares the nodes and accelerators and the manifest marks them as declared. The driver program also records what Spark itself reports (Spark version string, executor count and cores, `spark.plugins`).
  - Methodology: cold mode uses fresh executors but can't drop the OS page cache, so reports label it "cold (cache not dropped)". The quiet-cluster check uses the cluster's REST/UI API when reachable; otherwise the run is flagged "quiet check skipped".
  - Compatibility: `velocia engines check <engine> --cluster <name>` runs a smoke test (3 SQL queries, one small TeraSort, correctness checks) before any experiment, so an API gap shows up as a clear failure, not a broken benchmark.
- **Engine families** (plugin): own the driver program, the submission format, the unit tag scheme and the telemetry reader. `spark` is the only family through v1.0. A later family must provide the same things: run a unit, tag it, time it, report the same summary metrics where it can (missing ones are `null`, never invented), and compute correctness checksums with the same rules. SQL workloads can run across families (each family translates dialect); job workloads belong to one family.
- **Engines** (plugin): family + container image + configuration + supported family versions. Shipped: `spark-vanilla`, `spark-gluten` (Gluten + Velox), `spark-comet` (DataFusion Comet). Dockerfiles in repo; prebuilt images published to GHCR by digest with upstream `NOTICE` files, so a first run needs no local build. Spark version chosen from the engines' published compatibility matrices. Vendor accelerators are added as engine definitions, software (Gluten, Comet) and hardware alike (GPUs with Spark RAPIDS, Speedata's APU). A hardware accelerator engine is an image plus Spark conf pinned to a cluster whose nodes carry the device. Velocia needs only that, never the vendor's other tools.
- **Driver program** (`spark` family; shipped with each submission, not baked into images): for each unit sets the job description to `velocia:<run_id>:<unit_id>:<rep>`, executes it into its declared sink, records wall time from the driver, and writes `timings.json`.
- **Hardware probes** (plugin): describe the nodes for the manifest. Built in: CPU model, cores, memory, disk, network. Optional: NVIDIA GPUs. Other accelerators (for example an APU card) get a probe plugin that records model, count, driver and firmware versions; until one exists, the hardware profile states them and the manifest marks them as declared, not detected.
- Each run gets a `run_id`, its own event log directory, and `manifest.json`: image digests, Velocia git SHA, config hash, family, engine and Spark versions, hardware probe output for each node type (including accelerators), node count, hardware profile, dataset manifest ID, start and end time.
- Runs execute one at a time; dynamic allocation off; a quiet-cluster check (no other Spark apps, CPU idle below a threshold) runs before each run.

## 5. Methodology

| Rule | Requirement |
| --- | --- |
| Cold vs warm | Cold: fresh executors per repetition, OS page cache dropped where the runner allows (privileged local Linux, k8s privileged init container); otherwise labeled "cold (cache not dropped)". Warm: one explicit discarded warm-up, then repetitions in the same application |
| Repetitions | ≥ 5 per cell; median, p95, coefficient of variation for every measure; cells with CV > 10% flagged |
| Ratios | For every measure: ratio of medians vs the reference engine, with bootstrap 95% CI (10,000 resamples). Oriented so that > 1 always means "better than reference" (reference / candidate for lower-is-better, candidate / reference for higher-is-better). For wall time this ratio is the speedup |
| Correctness, SQL | One untimed pass per cell computes row count and an order-independent checksum (`sum(xxhash64(...))` over result columns, with floating and decimal values rounded to a configurable precision, default 4 decimals, because engines sum floats in different orders). Mismatch vs reference = failed result. A workload may opt a unit into tolerance mode (sorted, rounded results compared with a declared tolerance) for float-noise-only differences; the mode used is reported |
| Correctness, jobs | One untimed pass per cell runs the job's validator: exact checksums where the job is deterministic (TeraSort, Sort, WordCount, ETL), declared tolerances where it is iterative floating point (PageRank, KMeans). Failure = failed result |
| Timeouts | Per-unit timeout; timed-out units are reported as such, never dropped silently |
| Comparability | Results compared only within one hardware manifest, unless the experiment sets `comparison.allow_cross_hardware: true`. Cross-hardware reports carry a banner, list every hardware manifest, and must show at least one normalized measure (cost, node-hours or a custom unit) next to time |

## 6. Measures

Every measure is computed per unit and repetition, then goes through the same statistics (median, p95, CV, ratio with CI).

**Built-in measures**

| Measure | Unit | Direction | Source |
| --- | --- | --- | --- |
| `wall_time` | s | lower | Driver timing |
| `task_cpu_time` | s | lower | Event log |
| `task_run_time` | s | lower | Event log |
| `gc_time` | s | lower | Event log |
| `shuffle_bytes` | bytes | lower | Event log |
| `spill_bytes` | bytes | lower | Event log |
| `throughput_rows` | rows/s | higher | Input rows / wall time |
| `throughput_bytes` | bytes/s | higher | Input bytes / wall time |
| `node_hours` | node·h | lower | Wall time × nodes |
| `accelerator_hours` | device·h | lower | Wall time × nodes × hardware-profile accelerators per node (APU-, GPU-hours); `null` on clusters without accelerators |
| `cost_usd` | USD | lower | Wall time × nodes × hardware-profile price |
| `energy_kwh` | kWh | lower | Wall time × nodes × hardware-profile watts (estimate, labeled as such) |

**Custom measures** let a user or vendor define their own unit of measure, for example an accelerator vendor's "compute unit", without changing Velocia. Two ways:

1. **Declarative** (`measures/<name>.yaml`): a safe arithmetic formula over named inputs. It is evaluated by Velocia's own expression evaluator (AST allow-list, no Python `eval`):

   ```yaml
   name: vendor_cu
   unit: CU
   direction: lower
   description: "Vendor compute units consumed (definition supplied by the user)"
   formula: "unit.wall_s / 3600 * cluster.nodes * hw.cu_per_node_hour"
   ```

   Inputs: `unit.*` (wall_s, task_cpu_s, task_run_s, gc_s, input_rows, input_bytes, output_rows, shuffle_read_bytes, shuffle_write_bytes, spill_bytes, stages, tasks), `cluster.*` (nodes, executors, executor_cores, executor_memory_gb), and `hw.*` (every field of the cluster's hardware profile, including custom coefficients such as `cu_per_node_hour`).

2. **Python plugin** (`velocia.measures` entry point) for measures a formula can't express. It must be a pure, offline function of the same inputs.

Rules for all measures: no network access, no calls to other tools or services (the independence invariant); the measure definition and its hash go into the manifest; a missing input gives `null` with a reason, never a guess.

**Hardware profiles** (`hardware/<name>.yaml`) hold per-node coefficients that the hardware probe can't observe: price per node-hour, watts per node, accelerators per node, and any custom coefficients. They are versioned with the experiment.

## 7. Event-log summaries

A minimal streaming reader for Velocia's own finished event logs (plain or zstd, single file or rolling directory). Per unit (matched by job description tag; for an opaque unit, the whole application) it extracts: wall time, number of jobs, stages and tasks, summed task run time and CPU time, GC time, input rows and bytes, output rows and bytes, shuffle read/write bytes, spill bytes, and whether the plan contains fallback markers (row/columnar transitions) for accelerated engines. For job units it also reports the share of task time spent in stages without accelerated operators. Secrets in the environment and Spark configs are redacted on read.

## 8. Storage

```
velocia-results/
  catalog.duckdb                       # datasets, experiments, runs, results
  datasets/<dataset_id>.json
  runs/<run_id>/manifest.json
  runs/<run_id>/timings.json
  runs/<run_id>/eventlog/              # redacted
  results/<experiment_id>.parquet
  reports/<experiment_id>/index.html   # self-contained
  bundles/<experiment_id>.bundle.zip
```

| Table | Key columns |
| --- | --- |
| `dataset` | dataset_id, suite, generator_params, seed, scale, format, compression, row_group_size, files, bytes, checksum |
| `experiment` | experiment_id, name, yaml, created_at, velocia_version |
| `run` | run_id, experiment_id, cell_key, engine, cluster, config_hash, mode, rep, app_id, status, manifest_json |
| `unit_run` | run_id, unit_id, rep, wall_ms, status, summary metrics from section 7 |
| `measure_value` | run_id, unit_id, rep, measure, value, null_reason |
| `result` | experiment_id, cell_key, unit_id, measure, median, p95, cv, ratio, ci_low, ci_high, n, correctness |

## 9. Benchmark bundle export (v0.2)

`velocia bundle <experiment_id>` writes a versioned, self-describing zip that any analysis tool can consume (format in 04). It contains the experiment, dataset manifests, per-run manifests, hardware profiles, measure definitions, redacted event logs, results, and an explicit **pairing table**: for each unit and config, the median run of the reference engine and of each other engine. This is what analysis tools need to calibrate speedup projections.

## 11. Acceptance criteria

**v0.1**
- [ ] `pip install velocia` plus Docker is enough to run a TPC-H SF1 experiment end to end; no other service is started.
- [ ] TeraGen → TeraSort → TeraValidate runs as a job workload with per-unit timings and a passing validator.
- [ ] One command reruns a YAML experiment from scratch on a quiet machine; for ≥ 90% of cells the rerun's median falls inside the first run's 95% CI, and no ratio CI moves from "better" to "worse" than reference.
- [ ] Every result shows a correctness status; a planted wrong-result engine is reported as failed, for both a SQL and a job workload.
- [ ] Medians with CIs for vanilla Spark and at least one accelerated engine on TPC-H SF10.
- [ ] A custom declarative measure defined only in YAML appears in the report with medians and CIs; a formula that references an unknown input is rejected before the run starts.
- [ ] The static HTML report opens offline.
- [ ] Planted secrets in Spark configs appear nowhere in the results directory or reports.

**v0.2**
- [ ] A second accelerated engine works.
- [ ] The full job suite (section 1.2) runs on vanilla Spark with passing validators.
- [ ] `synth` workloads produce parameter sweeps with CIs; the same seed regenerates a dataset with the same checksum.
- [ ] The `external` runner runs an experiment on a Spark standalone cluster that Velocia didn't start, collects its event logs, and labels cold mode and declared hardware.
- [ ] A two-cluster experiment with `allow_cross_hardware: true` runs, labels the report, and shows a normalized measure; without the flag it is refused.
- [ ] Bundles validate against the published schema and include a complete pairing table.
- [ ] `velocia compare` refuses mismatched hardware manifests unless forced.

**v0.3**
- [ ] SF100 TPC-DS-derived run on one cloud provider with a hard budget cap; teardown verified even after failures.
